# Metric and control inventory

Audited against the current source and installed macOS 27 SDK on 2026-10-12. “Placeholder” below means an unavailable dash, an empty labelled graph or a disabled control. The app does **not** generate fake usage values. The exact CPU-only memory overlay is also not mocked: it is explicitly a residual estimate.

Two buckets describe the missing features. “Possible” includes work that would need a separately approved privileged helper or hardware-specific research; it does not promise that every Mac exposes a usable counter. “Not possible” means the exact Windows feature has no macOS equivalent, or the requested exact data is not obtainable under this app's ordinary-user, offline, no-helper constraints. It does not mean no Apple-internal tool or future OS could ever provide related information.

The privileged alternative for CPU speed is supported by the installed `powermetrics(1)` manual, which documents frequency sampling and process network/energy options. Running the ordinary-user command returned “must be invoked as the superuser.” Apple's [energy-efficiency guide](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/MonitoringEnergyUsage.html) also describes the tool and profiling workflow. Architecture is documented in Apple's [XNU proc_info.h](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info.h). Disk times are defined by Apple's [IOBlockStorageDriver header](https://github.com/apple-oss-distributions/IOStorageFamily/blob/main/IOBlockStorageDriver.h), including nanosecond total-time and latency counters; availability is driver-dependent.

## 2. Exact Windows behavior/data is not available on this Mac

| Feature | Why the exact feature is unavailable | Meaningful Mac alternative |
| --- | --- | --- |
| Windows Power usage / Power usage trend categories | Windows' classifications and scale have no exact macOS counterpart. | A separately labelled Mac energy estimate, if designed and measured later. |
| Windows kernel handles, handle count, UAC/elevation and registry/file virtualization fields | Windows object/security concepts do not exist as the same counters on macOS. File descriptors and Mach ports are different resources. | Add separately named descriptor/port/privilege fields where access permits. |
| Windows CPU affinity mask and Efficiency mode | There is no matching arbitrary foreign-process Windows affinity/EcoQoS control exposed by this app's public Mac APIs. | Windows GPU engine numbers/names and dedicated VRAM totals | WDDM engine identities do not exist on Apple silicon; its GPU uses unified memory. | Current renderer/tiler activity and driver-reported shared-memory counters. |
| Exact, disjoint “CPU used memory versus GPU used memory” split | CPU and GPU can reference the same physical allocations. Subtracting counters is not an independently measured CPU allocation total. | Total/system/GPU lines and clearly labelled CPU/other residual estimate. |
| Windows committed/paged/nonpaged pools, hardware-reserved RAM, DIMM slots/speed, and BIOS startup time | These exact Windows memory/firmware layouts do not map to this Apple silicon app. This ordinary-user build has no verified exact hardware-reserved RAM counter. | App/wired/compressed/cache/swap memory and Mac startup metadata where meaningful. |
| Retrospective all-app metered-network/notification history | No public ordinary-user API supplies another app's historical notification counts or Windows metered-network accounting. Data never observed cannot be recovered. | Explicitly opt-in future observed counters where a collection API exists; no invented backfill. |
| Directly toggling every other app's managed Login Item | `SMAppService` manages an app's own services, not arbitrary other applications' user-approved login registrations. | Open Login Items in System Settings; separately manage user-authored launchd jobs if designed and authorized. |

Apple's [SMAppService documentation](https://developer.apple.com/documentation/servicemanagement/smappservice) describes service management for an app and its helper executables. Apple's [Metal memory documentation](https://developer.apple.com/documentation/metal/choosing-a-resource-storage-mode-for-apple-gpus) explains shared/unified memory. These limits are distinct from features simply not implemented yet.

## Real features already connected

Process CPU, footprint memory, threads, identity/start time, executable/user/status and supported disk I/O and experimental per-process TCP/UDP receive/send rates; total/logical/kernel CPU history and uptime; physical/used/free/wired/compressed/cached/swap memory and pressure; local interface totals/rates/IPv4; mounted-volume capacity and separately labelled physical-device throughput; driver-provided GPU/renderer/tiler utilization and GPU memory; safe process actions; local startup/service/session inventory; opt-in observed CPU/disk history. Missing or denied readings remain unavailable rather than fabricated zeros. Pressure starts Unknown until a real reading/notification arrives.

## CPU speed and storage follow-up

The CPU speed experiment succeeds as an ordinary user on the development Apple silicon Mac. It dynamically resolves Apple's built-in private IOReport library, subscribes only to CPU complex state channels, and weights validated frequency-table entries by active residency. Fabric/CPM and idle states are excluded. Hz and kHz encodings are validated; missing symbols, unknown states, table mismatches and idle-only intervals produce unavailable readings. There is no shell sampler, helper, downloaded binary or third-party dependency. Private-API compatibility on other chips and OS versions is not guaranteed. [Primary research reference](https://github.com/kennss/SiliconScope/blob/main/docs/ioreport-channels.md).

Storage now filters out drivers with no whole media, labels virtual disk images explicitly, and joins mounted filesystems to their verified whole-device ancestors. Capacity values are refreshed every 30 seconds; byte rates remain live. Drive capacity and filesystem capacity are separate. Used space is filesystem capacity minus space available to ordinary writes; APFS snapshots/reservations/shared containers affect it, and sibling volume capacities are never summed. Unmapped volumes remain visible with unavailable device throughput. [Apple whole-disk and media APIs](https://developer.apple.com/documentation/diskarbitration/dadiskcopywholedisk(_:)).

## Experimental per-process network

The approved reader dynamically resolves Apple’s built-in NetworkStatistics framework, subscribes to TCP/UDP flow byte counters on one utility queue, and queries asynchronously at the existing sampling interval. It retains only process identity and byte counters; callback addresses, endpoints, names and payloads are discarded. PID plus XNU unique-process identity is matched to the process creation time to prevent reused-PID attribution. Each flow establishes its own baseline before producing rates; closed flows preserve only already-observed deltas. Unsupported APIs, inaccessible processes, missing baselines or a bounded flow-limit failure produce unavailable readings. App helpers are summed for app groups. These observed rates include loopback and can differ from physical-interface totals; bytes transferred before a flow is first observed cannot be reconstructed. This is an undocumented interface, so future OS compatibility is not guaranteed. No package, subprocess, privileged helper, packet capture or remote request is added.

Primary structures: Apple’s [network statistics descriptors](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/net/ntstat.h) and [unique process identity](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info_private.h).
